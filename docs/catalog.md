# The workload catalog

The catalog is how OnTrak knows about operating systems and Microsoft products without
shipping any of them. Every entry is a **manifest**: where the media comes from, what
hardware the guest needs, how much it should get, and whether a machine can be graded
automatically. Actual media lives in the operator's media store (`media/`, gitignored).

```bash
ontrak catalog groups                 # the groups and how many entries each has
ontrak catalog list --group linux     # entries, with media source and automation level
ontrak catalog show win-xp-sp3        # one entry: profile, plan, media status
ontrak catalog plan ubuntu-24.04      # how it would be provisioned, and how fast
ontrak catalog validate               # CI gate: every manifest is coherent
ontrak catalog refresh                # regenerate the Linux image group from the Incus remote
```

## Groups

| File | Group | Covers |
| --- | --- | --- |
| `catalog/windows-desktop.yaml` | `windows-desktop` | Windows 95 OSR2, 98SE, ME, NT 4.0 Workstation, 2000 Pro, XP SP3, Vista SP2, 7 SP1, 8.1, 10 22H2, 11 24H2 |
| `catalog/windows-server.yaml` | `windows-server` | NT 4.0 Server, 2000, 2003 R2, 2008 R2, 2012 R2, 2016, 2019, 2022, 2025 |
| `catalog/server-products.yaml` | `server-products` | Exchange Server 2019/SE, SQL Server 2019/2022, SharePoint Server SE — layered onto the Server entries |
| `catalog/office.yaml` | `office` | Office 97, 2000, XP, 2003, 2007, 2010, 2013, 2016, 2019, LTSC 2021, LTSC 2024, Microsoft 365 Apps |
| `catalog/linux.yaml` | `linux` | Curated distributions and Linux VM/desktop images |
| `catalog/linux-images.yaml` | `linux-images` | Generated by `ontrak catalog refresh` from every image the remote publishes |

Windows Server matters more than its volume suggests: DNS, DHCP and group policy can be
broken *at the server*, which is how those faults actually reach a service desk.

`office` entries are **layered**: an Office entry declares `requires: [win10-22h2]`, and the
image build combines the base Windows image with the Office media from the operator's store.
Office has never been freely redistributable, so every Office entry is `source: operator`.

## Media rules

| `media.source` | Meaning | What OnTrak does |
| --- | --- | --- |
| `free` | Freely redistributable (Microsoft evaluation ISOs, the Linux image server) | `ontrak media fetch` downloads it, verifying `sha256` when the manifest declares one |
| `operator` | Retail Windows, Office, anything end-of-life | Never downloaded. `ontrak media missing` lists exactly which files to place in `media/` |

```bash
ontrak media status        # present / fetchable / operator-required, with sizes
ontrak media missing       # what you must supply from your own licences
ontrak media fetch         # free media only; refuses anything else
```

A `file://` URL is accepted, which is what makes the download path testable and what lets
an operator serve evaluation media from a local mirror.

Microsoft evaluation media expires (90 days for desktop, 180 for Server). For a range that
runs all year, replace the evaluation entries' media with your own licensed ISO: the manifest
is the only thing that changes.

## Device profiles

Guests from before VirtIO cannot use it. Rather than special-casing each era in code, an
entry names a profile and the profile carries the devices and config:

| Profile | Devices | Notes |
| --- | --- | --- |
| `modern` | VirtIO-SCSI disk, VirtIO NIC, Secure Boot on | Windows 11, Server 2016+, Linux VMs. Add a vTPM for Windows 11. |
| `vista-era` | VirtIO-SCSI disk, VirtIO NIC, Secure Boot off | Vista → 8.1. VirtIO drivers come from the virtio-win ISO during setup. |
| `legacy-xp` | IDE disk, e1000 NIC | 2000/XP/2003: no native VirtIO. |
| `legacy-9x` | IDE disk, rtl8139 NIC, `-M pc -vga cirrus`, 512 MiB ceiling | 95/98/ME: no ACPI assumptions. No guest automation exists at this era, so those entries are marked `automation: none` and their scenarios are instructor-observed. |
| `linux-container` | No devices | System container: shares the host kernel, starts in about a second. |
| `linux-vm` | VirtIO-SCSI disk, VirtIO NIC | Boot loaders, kernel modules, desktop GUIs. |

## Automation levels

| Level | Meaning |
| --- | --- |
| `agent` | Incus agent over virtio-vsock: no network dependency. What 10/11/Server use. |
| `winrm-ps51` | Windows PowerShell 5.1 over WinRM: everything scenario scripts are written against. |
| `winrm-ps2` | XP SP2 → 2008 R2 era. Possible, but the image must enable it and install PowerShell 2.0. |
| `ssh` | Linux guests. |
| `none` | DOS-based Windows. Nothing can be driven remotely; keep such scenarios manual. |

## Provisioning plans

`ontrak catalog plan <entry>` (and the portal, when it provisions) resolves the fastest
path the host can actually deliver:

| Strategy | Typical cost | When it applies |
| --- | --- | --- |
| `warm-pool` | ~5 s | A pre-booted, unclaimed clone for that scenario exists. |
| `container-image` | ~8 s | Linux system container. |
| `clone-template` | ~45 s | The scenario template with its `clean` snapshot exists. |
| `image-launch` | ~90 s | The guest image is published but no template has been built yet. |
| `build-image` | hours | An operator task: turn media into an image (`ontrak image build`). |
| `unsupported` | — | Nothing can automate it (DOS-era platforms, `recipe: manual`). |

The planner is pure — it takes the host facts as arguments, so `ontrak catalog plan` never
touches Incus and the same code answers "why did this student wait four minutes?".

## Product builds (`product-on-base`)

Some entries are not operating systems at all: Exchange Server, SQL Server and
SharePoint in `catalog/server-products.yaml`, and `m365-apps-on-win11` in the Office
group. A product entry is a *base Windows image with the product installed inside it*,
and the manifest names both halves:

```yaml
  - id: sql-server-2022
    requires: [win2022]                                # the guest to launch
    media: {source: operator, kind: iso, filename: sql-server-2022.iso}
    install: {recipe: product-on-base, builder: product,
              script: infra/windows/products/sql-server.ps1}
```

Build the base first (`ontrak image build win2022`), then the product
(`ontrak image build sql-server-2022`): the builder launches the base, attaches the
media, runs the install script inside the guest over the Incus agent, restarts and
re-runs it every time the script says the product needs a reboot, and publishes
`ontrak-<entry>` when the script reports `ONTRAK-PRODUCT-OK`. The driver is
`infra/windows/apply-product-install.py`; the per-product notes and the lab run that
proves an install against real media are in
[product-builds.md](product-builds.md).

Three rules these entries add to the ones above:

- **`requires` is a build order.** `sharepoint-server-se` requires `sql-server-2022` —
  a farm needs its database server — so it is layered onto the *published* SQL image,
  not onto a bare Server. Nothing here is a shortcut around its base.
- **Media is `operator`, always, in one of two shapes.** `kind: iso` is attached as a
  CD-ROM and found in the guest by its probe file; `kind: archive` is pushed into the
  guest and unpacked there (which is how the Office Deployment Tool arrives). The
  builder knows the difference, and so does the descriptor it writes for the script.
- **The domain products make their own forest.** The golden image is not sysprep'd, so
  clones share a machine SID and a domain *join* cannot be trusted: the Exchange and
  SharePoint scripts promote their guest to the single domain controller of a
  single-machine forest instead. One machine, one domain — what a training range can
  honestly run.

## Adding an entry

```yaml
  - id: win2019-core
    name: Windows Server 2019
    edition: Core
    released: "2018-10"
    support: extended
    kind: vm
    family: windows
    media:
      source: free                 # or operator + filename
      kind: iso
      filename: Windows_Server_2019_Eval.iso
      url: https://example.invalid/Server_2019_Eval.iso
    install: {recipe: iso-unattended, builder: incus-windows, target: win2019}
    device_profile: modern
    resources: {cpu: 2, memory: 4GiB, disk: 60GiB}
    automation: agent
    scenario_families: [hardware, software, network, os, security]
    tags: [server, core]
    notes: Core has no desktop shell, so GUI scenarios do not apply.
```

`ontrak catalog validate` is the check that matters: it rejects an unknown device profile,
an entry that cannot be automated but explains nothing, free media with no URL, operator
media with no filename, a container with WinRM automation, a product entry whose `requires`
names something that does not exist, and the `incus-windows` builder on a pre-Secure-Boot
profile.

## Refreshing the Linux list

`ontrak catalog refresh` runs `incus image list <remote>: --format=json` and rewrites
`catalog/linux-images.yaml`. That file is committed, so the catalog works offline and in CI,
and re-running the refresh is how "every Linux distribution" stays true as the image server
grows. Hand-written groups are never touched.

```bash
ontrak catalog refresh --remote images    # default remote: images
ontrak catalog validate
```

## Licensing notes

- Retail Windows and Office media is **not** redistributed by OnTrak, and no ISO is ever
  committed to this repository (CI enforces that).
- Evaluation media has an expiry; replace it with licensed media for long-lived images.
- The Linux images come from the public Incus image server. Some of them (RHEL in
  particular) are subscription-licensed in production despite being freely pulled: keep
  such machines on the isolated lab bridge and offline.
- Volume activation, KMS and audit obligations remain the operator's responsibility.
