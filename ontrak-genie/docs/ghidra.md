# Ghidra headless analysis

`ghidra_analyze` lets the agent disassemble a binary and reason about it: an
ELF, PE, Mach-O, or firmware image sitting in the workspace. Ghidra is a JVM
application with hundreds of megabytes of analysers, so it is driven
out-of-process through the `analyzeHeadless` launcher that ships with a Ghidra
install — never embedded in the agent.

## Requirements

- **Ghidra 11 or 12.** The install is found automatically in the usual places
  on Windows, macOS and Linux, or explicitly through `GHIDRA_HOME` /
  `GHIDRA_INSTALL_DIR`.
- **A JDK.** Ghidra needs Java 17+ (21 recommended). Set `JAVA_HOME` or put
  `java` on `PATH`.

On Windows the launcher is `support\analyzeHeadless.bat`, which cannot be
spawned directly — the tool runs it through `cmd.exe`. The official Windows
installer puts Ghidra under `%LOCALAPPDATA%\Programs\ghidra_<version>_PUBLIC`,
so the parent folder is scanned rather than version-guessed.

Nothing is installed by the agent, and no Ghidra extension is required.

## Usage

```
ghidra_analyze { "path": "samples/invoice.exe", "timeoutSeconds": 600 }
```

`path` is workspace-relative. The tool refuses anything that is not a file,
empty files, and anything over 512 MB.

The model receives a compact text summary: language and processor, compiler,
entry points, imports, exported symbols, a function sample, and **indicator
strings** (URLs, IP addresses, absolute paths, shell commands, tooling names)
promoted out of the general string list. The full JSON summary is written to
`.genie/ghidra/<name>-<timestamp>.json` in the workspace so an operator can see
exactly what the model saw.

## How a run works

1. The binary and `ghidra/ExportSummary.java` are copied into a temp project
   directory. Ghidra refuses any path containing a `.`-prefixed element, which
   a checkout under `~/.config/...` runs into immediately; staging also means a
   binary cannot change underneath the analyser.
2. `analyzeHeadless <project> <name> -import <binary> -scriptPath <scripts>
   -postScript ExportSummary.java <out.json> -deleteProject -overwrite`
3. The post-script walks the imported program and writes the JSON summary.
4. The summary is parsed, formatted and persisted; the temp project is deleted.

Analysis is read-only with respect to the binary. The temp project is removed
in a `finally` block even when the analyser fails.

## Availability

`primeGhidra()` resolves the install once per process, before the turn builds
its tool list, alongside `primeMcpTools()`. When no install is found the tool is
not offered at all, so the model is never told it can do something it cannot. If
Ghidra appears at runtime without a restart the tool explains what to install
rather than failing silently.

## Tests

```
npm run build
node --test dist/test/ghidra.test.js
```

The suite covers detection, argument construction, summary validation,
indicator extraction, and a full spawn against a stub launcher. The live test
at the end runs **real** Ghidra against `ghidra/fixtures/ghidra-probe-x86_64`
and is skipped (with a message) on hosts without a Ghidra install.

`ghidra/fixtures/ghidra-probe-x86_64` is a 193-byte ELF64 x86-64 executable: an
ELF header, one `PT_LOAD` (read + execute) segment, and a `write` + `exit`
body. It is generated byte for byte by `node ghidra/make-test-binary.mjs`, so no
cross-compiler is needed; commit a regenerated fixture rather than editing it.

Verified on Ghidra 12.1.4 with JDK 21: the fixture imports as
`x86:LE:64:default`, entry point `00400078`, one function (`entry`).
